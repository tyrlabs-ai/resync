# RepoSync V1 normative behavior

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are interpreted as described by RFC 2119.

## Objective and scope

RepoSync coordinates fully materialized Git worktrees on Linux. Each subscription names exactly one project, local path, Git remote, and synchronization branch. Subscription is explicit. RepoSync MUST NOT discover and modify unrelated directories.

Git commits, objects, and a protected shared branch are the revision and transport substrate. Projection filesystems, partial hydration, secret transport, general path classification, submodules, LFS, sparse checkout, and semantic conflict resolution are not V1 features.

## Project and checkout identity

A synchronization universe is identified by the tuple `(canonical service origin, project_id)`. Git ancestry establishes compatibility but MUST NOT be used as project identity: two clones with identical commits may intentionally synchronize independently.

Every enrolled physical checkout has a distinct `checkout_id`. Project and checkout identity MUST be stored in machine-local RepoSync state and Git-local configuration, not as the sole value in a tracked `.resync.toml`. An ordinary clone of a non-RepoSync remote therefore does not accidentally inherit enrollment.

Cloning a RepoSync service URL that embeds a project ID MAY offer to join that project. Otherwise the client MUST require an intentional operation:

- `init` creates a new project ID.
- `join` enrolls the checkout into an existing project ID.
- `fork` creates a new project ID seeded from the current Git state.

When peers report different non-empty project identities, automatic synchronization MUST stop. Neither ancestry nor modification time may silently choose a winner.

## Shared branch

The configured branch is the serialization point for accepted work. A conforming remote MUST reject non-fast-forward updates, force pushes, and branch deletion. RepoSync MUST never rewrite a commit after it has been accepted by that branch. A client MAY rewrite unpublished commits while rebasing them onto an accepted head.

The Git remote is authoritative. A catalog advertisement is a discovery hint and MUST NOT be presented as proof of publication. Only a successful Git push proves that a publisher won the ref-update race.

## Workspace generations and leases

A daemon manages many repositories but serializes mutations per repository. Every successful reconciliation increments a local monotonically increasing workspace generation.

Participating agent tool calls, including reads, MUST acquire an activity lease before accessing a managed worktree and MUST release it after the call returns. Reconciliation MUST hold an exclusive lease and MUST wait for all activity leases to end. New activity leases MUST wait while reconciliation is active. A lease covers one observable call only; detached children are unmanaged after the call returns.

## Fetch and installation

Fetching objects MAY occur at any time because it does not alter the visible worktree. When a newer remote head is fetched, the project enters `REMOTE_AHEAD`. The daemon installs it at the earliest exclusive lease boundary.

Before installation the daemon captures at least HEAD, the index tree, the complete tracked working tree, relevant untracked paths, the prior accepted remote OID, and the target OID. It creates private synthetic index and working-tree commits, rebases the complete unpublished chain in isolation, and reverifies the active snapshot before installation.

A clean result MUST preserve staged versus unstaged changes, tracked modes and symlinks, and non-colliding untracked files. A mechanical conflict, an untracked-path collision, a rewritten remote base, or a changed active snapshot MUST reject installation. A rejected candidate MUST NOT partially modify the active worktree.

## Publication

Only ordinary logical commits are publishable; synthetic and recovery commits MUST NOT be pushed. Before publication the daemon fetches again, rebases against the final observed head, validates the publishable commit in an isolated worktree, and performs a normal push. Non-fast-forward rejection causes a bounded retry. Successful validation means only that configured commands passed for that parentage; a clean merge alone is not semantic validation.

## Conflict and failure behavior

Primary states are `MATERIALIZING`, `CURRENT`, `REMOTE_AHEAD`, `WAITING_FOR_LEASES`, `RECONCILING`, `CONFLICTED`, `OFFLINE`, and `FAILED`. Durability is orthogonal: `NO_LOCAL_CHANGE`, `DIRTY_UNCHECKPOINTED`, `COMMITTED_UNPUBLISHED`, `PUBLISHING`, or `REMOTELY_DURABLE`.

On conflict the prior coherent workspace remains visible, all inputs remain recoverable, and ordinary managed calls are blocked. Inspection and explicit resolution/recovery operations remain available. The status surface MUST distinguish currentness from remote durability and MUST say whether local work is safe.

An activated project remains usable offline. Local commits and recovery data remain durable and publication queues until connectivity returns. Remote freshness is explicitly unknown while offline.

## Correctness invariants

1. Captured local work is never silently discarded.
2. Fetching never mutates the visible worktree.
3. A participating call observes one generation.
4. Installation occurs only with the exclusive lease.
5. Synthetic commits are never pushed.
6. Publication never uses force.
7. A failed transform leaves the active workspace coherent and recoverable.
8. A mechanically clean transform is not described as semantically validated.
9. Crash recovery is journaled, deterministic, and idempotent.
10. Every participating checkout agrees on the same service origin and project ID.
11. Every enrolled machine has an independently revocable device identity.
